# DailyBrief Next.js Web Service Design

## Goal

Turn DailyBrief from a local static-report generator into a deployable web application that can be accessed through a domain, generates the daily brief automatically, exposes historical reports, and provides a password-protected source management interface.

The migration must preserve the current report style and core generation logic. The first web version should wrap the existing engine instead of rewriting fetching, LLM enrichment, or report rendering.

## Non-Goals

- Do not redesign the generated report content area in the first migration.
- Do not remove `daily_reports/` output compatibility in the first migration.
- Do not support deleting sources in the first source manager. Disable is the safe alternative.
- Do not replace DeepSeek or the existing LLM backend dispatcher.
- Do not add multi-user roles in the first version.

## Technical Stack

- Framework: Next.js App Router.
- Styling: Tailwind CSS for new web/admin pages.
- Database: PostgreSQL running in Docker.
- Database access: Prisma, with migrations committed to the repo.
- Deployment: Docker Compose.
- Runtime split: web service plus worker service.
- Existing TypeScript modules remain the core engine.

## Existing Logic To Preserve

The following modules remain authoritative:

- `lib/sources/dispatch.ts`: source fetch routing.
- `lib/sources/types.ts`: source and article shape.
- `lib/ai/llm.ts` and backend modules: LLM dispatch.
- `lib/ai/pipeline.ts`: daily report generation.
- `lib/output/render.ts`: current generated-report HTML and CSS.
- `scripts/daily.ts`: reference orchestration flow.

The first implementation should extract orchestration into reusable functions instead of making Next.js pages shell out to scripts.

## Architecture

### Web Service

The `web` container serves:

- Public pages for today's report, report history, and individual report dates.
- Password-protected admin pages for source management and generation runs.
- API routes for admin actions.
- Static compatibility routes for generated report HTML when useful.

### Worker Service

The `worker` container runs the scheduled generation loop:

- Reads `REPORT_TZ` and a configured daily run time.
- Acquires a generation lock so only one run happens at a time.
- Fetches enabled sources for the active locale.
- Calls the existing enrichment and digest pipeline.
- Saves report JSON, rendered HTML, article cache, and run metadata.
- Keeps writing `daily_reports/<date>/` for compatibility during migration.

### PostgreSQL

Postgres becomes the source of truth for web operation:

- Source configuration.
- Report metadata and generated content.
- Article caches.
- Generation run history.
- Optional session records if signed cookies alone are not enough.

## Data Model

### `sources`

Stores source configuration.

Fields:

- `id`: stable unique string, primary key.
- `name`: display name.
- `type`: `rss`, `api`, or `scrape`.
- `url`: source URL.
- `category`: `tech`, `finance`, or `politics`.
- `subcategory`: optional grouping key.
- `enabled`: boolean.
- `use_curl`: boolean.
- `lang`: optional `zh` or `en`.
- `locales`: string array containing `zh` and/or `en`.
- `keywords`: string array.
- `notes`: optional text.
- `created_at`, `updated_at`.

Migration rule: import existing `sources.config.json` into this table. Keep a one-time or repeatable sync tool so local forks can bootstrap quickly.

### `reports`

Stores one generated report per date and locale.

Fields:

- `id`: generated primary key.
- `date_key`: `YYYY-MM-DD`.
- `locale`: `zh` or `en`.
- `status`: `generating`, `ready`, or `failed`.
- `report_json`: JSONB from `DailyReport`.
- `html`: full rendered report HTML generated by `renderHtml()`.
- `summary`: optional text for archive previews.
- `generated_at`.
- `created_at`, `updated_at`.

Unique key: `(date_key, locale)`.

### `report_articles`

Stores fetched and enriched article cache for a report.

Fields:

- `id`: generated primary key.
- `report_id`: foreign key.
- `source_id`.
- `source_name`.
- `category`.
- `title`.
- `url`.
- `excerpt`.
- `summary`.
- `meta`.
- `published_at`.
- `raw_json`: JSONB for future compatibility.

### `generation_runs`

Stores every manual or scheduled generation attempt.

Fields:

- `id`: generated primary key.
- `date_key`.
- `locale`.
- `trigger`: `schedule`, `manual`, or `startup`.
- `status`: `running`, `success`, or `failed`.
- `started_at`, `finished_at`.
- `articles_count`.
- `llm_backend`.
- `error_message`.
- `log_excerpt`.

## Public Pages

### `/`

Shows today's report if available. If today's report is not ready, show the latest ready report with a small status note.

### `/reports/[date]`

Shows the report for a specific date.

The first version should expose this through a Next.js route handler that returns the saved full HTML response with `Content-Type: text/html`. This preserves the current report styling, embedded CSS, and tab behavior exactly. A later iteration can add a React wrapper only after the generated report surface is stable.

### `/archive`

Lists available reports by date, locale, generation status, and brief summary.

## Admin Pages

All admin routes require password authentication.

### `/admin/login`

Single password login. Password is configured with `ADMIN_PASSWORD` or a hashed variant.

### `/admin`

Overview:

- Latest report status.
- Last generation run.
- Next scheduled run.
- Active source count.
- Failed source or generation warnings.

### `/admin/sources`

Source management:

- List all sources.
- Filter by category, subcategory, locale, enabled state, and type.
- Edit existing source fields.
- Add a normal RSS source.
- Enable or disable a source.
- Validate before save.
- Test one source and show fetched item count plus sample titles.

Deletion is intentionally omitted. A disabled source preserves history and notes.

### `/admin/runs`

Generation operations:

- View run history.
- Trigger today's generation.
- Trigger a specific date generation.
- See current running state.
- See failure message and log excerpt.

## Source Management Rules

First version supports adding ordinary RSS sources from the UI. It does not promise that arbitrary API or scrape sources can be added without code, because special fetchers still require branches in `fetchSource()`.

For API and scrape sources:

- Existing records can be edited, enabled, disabled, and tested.
- New API or scrape sources are blocked in the first UI because they require code support in `fetchSource()`.

Validation:

- `id` must be unique, lowercase-friendly, and stable.
- `name`, `type`, `url`, and `category` are required.
- `type` must be one of `rss`, `api`, `scrape`.
- `category` must be one of `tech`, `finance`, `politics`.
- `locales` must contain `zh`, `en`, or both.
- `keywords` are optional.

## Generation Flow

1. Worker starts a `generation_runs` row with status `running`.
2. Worker loads enabled sources from Postgres for the active locale.
3. Worker fetches sources using existing `fetchSource()` behavior.
4. Worker enriches article summaries using existing logic.
5. Worker calls `generateDailyReport()`.
6. Worker groups raw articles and calls `renderHtml()`.
7. Worker writes or updates the `reports` row.
8. Worker writes `report_articles` rows.
9. Worker writes compatible files under `daily_reports/<date>/`.
10. Worker marks the run as `success` or `failed`.

Failure behavior:

- Per-source fetch failures remain non-fatal.
- A failed LLM or render step marks the run failed.
- If a previous report for the date exists, public pages keep serving the previous ready version.

## Authentication

First version uses one admin password.

Recommended implementation:

- `ADMIN_PASSWORD_HASH` preferred.
- `ADMIN_PASSWORD` allowed for local development.
- Login sets an HTTP-only signed cookie.
- Admin API routes verify the cookie.
- Public pages do not require auth.

Security boundaries:

- Admin source save and manual generation must require auth.
- Test source must require auth because it can access external URLs.
- Manual generation should have a lock to prevent duplicate LLM usage.

## Deployment

Docker Compose services:

- `web`: Next.js app.
- `worker`: scheduled generation worker.
- `postgres`: PostgreSQL database.
- Optional `nginx` or use an existing reverse proxy on the server.

Required environment:

- `DATABASE_URL`
- `DEEPSEEK_API_KEY`
- `LLM_BACKEND=deepseek`
- `REPORT_LOCALE`
- `REPORT_TZ`
- `ADMIN_PASSWORD` or `ADMIN_PASSWORD_HASH`
- `DAILY_RUN_TIME`
- `SESSION_SECRET`

Persistent volumes:

- Postgres data.
- `daily_reports/` compatibility output.
- `logs/` if file logs remain.

## Migration Plan

1. Add Next.js, Tailwind, and database tooling.
2. Add Postgres schema and migration scripts.
3. Import `sources.config.json` into Postgres.
4. Extract reusable daily generation service from current scripts.
5. Add public report and archive pages.
6. Add admin auth.
7. Add source management.
8. Add worker scheduler.
9. Add Docker Compose deployment.
10. Add verification docs for local and server deployment.

## Testing

Automated checks:

- TypeScript check.
- Existing render smoke test.
- Source validation tests.
- Source API save validation tests.
- Auth-protected API tests.
- Generation service unit tests using mocked LLM where possible.

Manual checks:

- Login and logout.
- Add RSS source, test it, disable it.
- Trigger manual generation.
- Visit `/`, `/archive`, and `/reports/[date]`.
- Restart containers and verify reports and source config persist.

## Design Direction

Reading this as a productized internal publishing/admin app for a technical operator, with a restrained Apple-like editorial surface for public reports and a quiet utilitarian admin language for source operations, leaning toward Next.js App Router plus Tailwind with CSS variables reused from the current report style.

Design dials:

- `DESIGN_VARIANCE: 5`
- `MOTION_INTENSITY: 3`
- `VISUAL_DENSITY: 6`

Public report pages should keep the current generated report look. Admin pages should be compact, scan-friendly, and calm: table/list on the left, editable detail panel on the right, clear status and test results, no marketing hero.

## Open Implementation Notes

- Prefer preserving `renderHtml()` output for report detail pages in version one.
- Consider a later React-native report renderer only after the web app is stable.
- Keep `sources.config.json` as an import/export compatibility format, not the live source of truth.
- Avoid deleting old local CLI commands. They remain useful for debugging and local fallback.
